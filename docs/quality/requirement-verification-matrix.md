# Requirement Verification Matrix

This matrix maps only the launch-critical Phase 1 PRD requirements and their unhappy paths. It uses the current `docs/PRD.md`, `docs/quality/capability-matrix.md`, and `docs/quality/launch-baseline-2026-04.md` as controlling inputs.

## Traceability Caveat

- `tests/registry.yaml` and the scenario markdown files still carry legacy `REQ-*` identifiers in `prd_ref`.
- This matrix is therefore a maintained translation layer from those legacy scenario references to the rewritten launch-only `REQ-P1-*` requirements in `docs/PRD.md`.
- Until the registry is re-keyed, treat scenario IDs as the evidence source and this document as the Phase 1 traceability bridge.

## Selection Rules

- Include only `REQ-P1-*` requirements.
- Include unhappy paths when they are the real launch risk for a requirement.
- Treat backend scenario tests as the strongest evidence.
- Treat web/mobile integration tests, Playwright, and Maestro flows as useful only when they demonstrate observable outcomes.
- Treat shell-only, mock-only, existence-only, and snapshot-like checks as ceremonial, not blocker evidence.

## Signal Legend

| Signal       | Meaning                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `blocker`    | Backend scenario or contract evidence proves the requirement or unhappy path with an observable outcome.                  |
| `advisory`   | Web/mobile/Playwright/Maestro evidence shows the flow or UI outcome, but the proof is not authoritative backend coverage. |
| `ceremonial` | Shell-only, mock-only, existence-only, or snapshot-like evidence. Useful for wiring, not for launch confidence.           |
| `missing`    | No direct verification evidence found for the requirement.                                                                |

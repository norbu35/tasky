# Frontend Alignment Matrix

**Date:** 2026-04-10
**Status:** hardened -- reflects post-Tranche-4 state
**Plan:** `docs/plans/2026-04-10-frontend-alignment-and-scope-hardening.md`

This matrix classifies the current frontend surface against `docs/PRD.md`, `docs/quality/launch-baseline-2026-04.md`,
`docs/API.yaml`, and the route trees in `apps/web/src/router/AppRoutes.tsx` and `apps/mobile/src/app/`.

## Decision Summary

- Manual tasker verification remains **launch-live**. The PRD and launch baseline defer only DAN fast-path
  verification, not manual verification.
- Monetization, wallet, referrals, subscription, instant match, B2B, OTP auth, and AI profile polish do **not**
  belong in active web or mobile navigation for Phase 1.
- Some future UI is worth preserving, but only outside active route trees:
  - web: `apps/web/src/future/`
  - mobile: `apps/mobile/src/future/`
- Thin placeholders with TODO-only behavior should be deleted instead of hidden behind inactive routes.

## Classification Key

- `launch-live`: reachable in launch apps and must be polished
- `implemented-gated-backend-only`: backend/runtime path exists, but launch clients must not expose it
- `deferred-substantial`: future-facing UI worth preserving in `future/`
- `deferred-shell`: thin or incomplete future UI that should not survive in active app trees
- `delete`: duplicate, misleading, or obsolete surface with no strong reason to preserve

## Ambiguities Resolved

### Manual verification stays

The launch baseline defers only `DAN verification`, not the entire tasker verification journey. Manual tasker
verification therefore stays launch-live on both web and mobile, including admin verification review surfaces.

### Admin features stays

`/admin/features` remains launch-live even though it manages dormant toggles, because the PRD explicitly keeps feature
toggle management in the Phase 1 admin toolset. The admin page must survive, but the exposed toggle descriptions and
surrounding docs should not imply dormant features are activation-ready.

### Wallet and payouts leave the clients even though backend code exists

`escrow_enabled` is a real backend activation candidate, but the launch baseline still excludes wallet/payout client
exposure. Client pages should therefore leave the active apps even if their code is preserved in `future/`.
